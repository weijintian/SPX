# iOS Acceptance Test Matrix

Run these checks on a current iPhone simulator for layout and on two physical devices for camera, microphone, calls, media library and network behavior. Include one iOS-to-Android pairing for cross-platform chat and calls.

| Area | Acceptance path | Expected result |
| --- | --- | --- |
| Authentication | Register, email verification, sign in/out, restore session, reset password | Clear validation, one session per account, no stale private cache after account switch |
| Chat | Text, emoji, reply, edit, delete, forward, multi-select, group mentions, draft | Correct ordering and ownership; reopen at latest message; no duplicate messages after reconnect |
| Media | Multi-select photos/videos, camera, file import, large video, interrupted upload, retry, save/forward in viewer | Correct iOS picker, visible progress, recoverable failures, valid saved media and no chat re-fetch loss |
| Video streaming | Open a large remote video before it is fully downloaded, seek to middle/end, deny network, retry, leave viewer, use a cached complete file | Bounded 206 byte ranges; prompt playback or a visible retry error; no compulsory full-file download; pending ranges cancel when the viewer closes |
| Shared video cancellation | Request the same range concurrently for poster and playback; cancel one reader, then cancel the last; clear account cache during a pending range and during full-file assembly | Canceling one reader preserves the remaining reader and shared request; the last cancellation stops network work; cache clearing wakes pending readers with cancellation and canceled assembly does not repopulate the cache |
| Download responsiveness | Download a large file with known and unknown content length while scrolling; leave and reopen the view; clear cache or change account while downloading | Unknown-size progress remains indeterminate; progress never moves backward and completion appears promptly; UI update frequency stays bounded and stale callbacks do not affect a new attempt/account |
| Upload recovery | Start a large chat attachment, lock device/app switch, simulate system termination and background relaunch, then force-quit/reopen, retry after checkpoint expiry, sign out while uploading | Acknowledged chunks are reused; one pending message/client ID remains; system scheduling is respected; force-quit resumes only after reopen; no cross-account uploads; a 24-hour-expired checkpoint restarts consistently |
| Upload responses | Upload a video with HTTP 201 and a valid code=0 envelope; repeat with a UTF-8 BOM, malformed body, business rejection and a missing media URL | Valid responses produce one playable message; malformed or incomplete responses keep the local attachment for retry; business errors retain the server explanation |
| Upload responsiveness | Upload a large video while scrolling history and sending text; fail and retry the upload; switch accounts during registration and completion | Text delivery remains independent; progress is monotonic within an attempt and resets on retry; old callbacks do not alter the current account; no duplicate send or attachment loss |
| Chat history and keyboard | Scroll away from the latest message, open/dismiss the keyboard, receive messages, load older history, then tap return to latest | Reading position remains stable; new messages do not pull the reader down; return-to-latest works; input and latest message remain visible when following the bottom |
| History cancellation | Load older history over a slow connection, leave the view or clear local history before the request fails; repeat with a failure in the current visible request | Canceled or cleared requests do not restore stale messages or show stale errors; loading state finishes; a current network failure still displays a retryable explanation |
| Group system notices | Join/invite/remove a member and change group metadata; compare Android; send an ordinary welcome message | Server-marked system notices are centered muted text without avatar, bubble or actions; user-authored welcome text remains an ordinary message |
| Thumbnail reuse | Scroll local and remote image/video previews off/on screen; send a transparent PNG or GIF; clear cache and switch accounts while thumbnails load | Previews reuse cached decoding; PNG/GIF bytes are preserved; a slow result never appears under another account; canceled video work releases decoder capacity |
| Policies | Read both texts while logged out and in settings, toggle consent, register/sign in | Bundled texts load offline; consent starts unchecked; account deletion is not misrepresented as an implemented workflow |
| Group | Create/join, announcement, members, roles, mute, remove, owner transfer, leave/dissolve | Actions respect server permissions and refresh the current group/list |
| Calls | Foreground audio/video, reject/timeout, minimize/move/restore, end, permission denial, Bluetooth route | Correct two-device state and audio ownership; no stale SDK callback ends a newer call |
| Calls in background | Lock screen, app switch, terminated app, network transition | Incoming call only passes when APNs/PushKit and server delivery are integrated; otherwise record as blocked |
| Red packets | Direct and group send, ordinary/random, claim race, expired/exhausted, uncertain response, history | No duplicate debit; received amount and claim list match server; history opens the correct packet |
| Mall / buyer | Product CNY price, live token estimate, SKU/stock races, checkout quote, payment result, delivery, cancel, after-sale and return | CNY stays fixed; server quote controls payment; each permitted status transition appears once |
| Merchant | Reapply after rejection, batch image upload/reorder, draft, publish, batch offline (50 max), inventory, ship/deliver/redeem, after-sale reply | Server validation is surfaced, inventory is not stale, no merchant-side refund approval is exposed |
| Wallet | Bind, deposit verification, withdraw, fee truncation, exchange, staking/redeem, interrupted request | Idempotency/recovery protection prevents duplicate financial operations; displayed amounts match server |
| Staking phase and quota | Compare iOS, Android and the same staking.plans response; switch phases; test zero/missing quota and a closed phase | Phase number/name, total and remaining rewards quota reflect server values; quota is labeled dividend plus referral rewards rather than principal capacity; closed/exhausted phases disable new submissions |
| Staking layout | Open on a narrow iPhone and iPad, with large amounts, accessibility text sizes, VoiceOver and light/dark appearance | Phase, quota, active principal, stakeable balance, rules, all plans and record details remain readable without clipped numbers or controls; long detail rows stack vertically |
| Staking input | Test empty/decimal/leading-zero input, 100000 increments, plan minimum, insufficient balance, the cumulative 10000000 boundary and incomplete plan/wallet data | Invalid or incomplete inputs cannot submit; limits match the server; the full-term estimate follows the selected plan and never treats missing values as zero |
| Staking account and recovery | Change accounts during slow loads and before an original-application retry; interrupt submission, reopen and safely retry or resolve the original request | Old responses do not overwrite the current account; a pending request keeps its original client_request_id and account; no duplicate stake or cross-account retry occurs |
| Staking settlement and records | In a configured test account, verify daily/ten-day estimates, a short final period, maturity settlement and the manual redeem fallback; repeat an interrupted operation | Estimates match principal times APY times days divided by 36500; actual paid amounts/status match server; principal is returned only once; dividends and returned principal do not become stakeable |
| Accessibility/layout | Dynamic Type, VoiceOver, light/dark, narrow iPhone, iPad, keyboard, safe areas | No clipped controls or overlapping content; destructive/financial actions are labeled and confirmed |

Attach Xcode build/test logs and device/OS versions when recording results. No test should use real funds or publish a live product without an explicitly configured test account and sandbox procedure.
